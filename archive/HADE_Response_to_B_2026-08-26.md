## 一、你找到的真 bug —— 确认

`check_electron_safety.py` 第 51–53 行：

```python
if not is_electron:
    print("ⓘ 未检出 electron 依赖 —— 本脚本只适用于 Electron 项目，跳过")
    return 0          # ← 退出码 0
```

而我们的 `AGENT-SETUP.md` 写着「退出码 0 = 通过」。

**结果**：在非 Electron 项目上跑这个校验器会得到"通过"。依赖检测因任何原因失效——monorepo 结构、electron 装在别名下、依赖字段挪位——脚本会静默报"三件套齐备"。

这正是我们自己 §九 反复强调的那类错误：**"不适用"被当成"通过"**。它长在数据安全校验器里，是本轮最讽刺的一处。

**你的 §10.3 四值退出码是正解，我们采纳：**

```
0 = pass    1 = findings    2 = unsupported（不代表通过）    3 = tool_error
```

一并采纳 `--json` 输出、`applicable` 字段、以及「每个 validator 必须有 pass / fail / unsupported / invalid_input 四类 fixture」。

### 2.3 hook 触发 —— R1 的解，也是你方案缺的那块

我们随后验证了 `PostToolUse` hook：

| 触发机制 | 实测 |
|---|---|
| skill description 概率匹配（两种形态） | **0/9** |
| hook 挂「文件被改」这一客观事件 | **3/3** |

实验设计分离了 hook 与 Global 的贡献：让模型改 `version` 号——无害操作、不碰数据定位字段、Global 的三问不应触发，**因此模型若提到三件套，只能来自 hook**。

- **对照组（无 hook）**：「version 改好了，数据定位路径不受影响」——未发现三件套缺失
- **实验组（有 hook）×3**：3/3 全部发现，**且是采纳不是复述**

判"采纳"的硬证据：某次回复出现「`electron/main.js` 只有 8 行」——**这个数字校验器从未输出**，工具序列里多了一次 Bash，模型自己去读文件核实了。

**三条机制事实**（对官方文档 + 实测双重确认）：

1. `matcher` 只匹配工具名；路径匹配要用 `if` 字段的 permission rule 语法
2. stdin 信息充足：`tool_input{file_path, content}` + `tool_response{...}` + 12 个顶层字段
3. **`PostToolUse` 的 stdout 不进上下文；但 `exit 2` + stderr 进**

第 3 条是你的架构里没有覆盖的通道。它意味着：**确定性检查可以不依赖模型"想不想调工具"。**

### 2.4 一条你会关心的规律：能力充分时工具会被跳过

5 次跨场景实测印证：模型知识够用时，不认为需要再调工具。
典型表现是「手算过了，不用等脚本」——即使脚本就在手边、skill 已装好。

**当装载决策交给模型自己判断时，它在"我已经会了"的场景下会系统性地不装载。**
