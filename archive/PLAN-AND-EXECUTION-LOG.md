# HADE 形式重构 Plan — 从单文件快照到可安装体

> 起草：2026-08-24 · 状态：**待确认，未执行**
> 本文件是**项目材料，不是 Global 材料**（§八.10 注）。确认后按批次执行，执行完毕本文件归档，不并入 Global。

---

## §0 一句话

把 HADE 从「**一个 91KB 单文件 + 手工 cp 日期快照**」重构为「**可安装、可版本化、可测量的 plugin 双件套**」——
**人格层的实例化原子性一步不让**，能力层第一次获得独立形体。

---

## §1 目标与非目标

### 目标

| # | 目标 | 现在的痛点 |
|---|------|-----------|
| G1 | 实例化原子性**不降级**（硬约束，一票否决） | 现在已达成，重构不得破坏 |
| G2 | 能力层可**独立分发**给别人 | 现在和人格层糊在一个文件里，无法分离 |
| G3 | **版本化 + 可回滚** | 现在是 `cp` + 日期后缀 + 留 3 份，无版本语义、无安装动作、换机器手工归位 |
| G4 | 触发率**可测量** | 现在"可触发性"（§八.10 五问之一）只能靠 HADE 自评 |

### 非目标（明确划掉，防止范围蔓延）

- ❌ **不改任何规则的内容**——这一轮只动**形式**，不动**内容**。任何"顺手优化一下这条措辞"都是越界（§四 铁规则 1 的精神）
  - 注：§6.6 的校验脚本**不算违反**（只把已有数值约束可执行化，不改一个字），但它是**新增能力**而非搬家，故单列为可选扩展待确认
- ❌ 不拆人格层
- ❌ 不做 agent 化
- ❌ 不做 Organon 本身，只做它的地基

## §2 架构：三层

```
┌── 层1 · 人格层（常驻，加载即实例化）───────────────────┐
│  ~/.claude/CLAUDE.md   ≈629 行                        │
│  §零 元规则 · §一 启动 · §二 7步 · §三 对话习惯          │
│  §四 铁规则 · §五 标记 · §八 身份/根隐喻/共舞/错误观/五问  │
│  §七 破坏性预警（安全，不可按需）                        │
│  + 高危哨兵行 ──────────┐                             │
└───────────────────────│───────────────────────────┘
                         │ 指向
┌── 层2 · 唤醒层（确定触发，非概率匹配）─────────────────┐
│  SessionStart hook → stdout 一句指针：                 │
│  "HADE 本体在 ~/.claude/CLAUDE.md，立刻完整读取"        │
│  作用：把「实例化」从「description 概率匹配」            │
│        换成「hook 确定触发 + 一次确定的 Read」           │
└───────────────────────────────────────────────────┘
┌── 层3 · 能力层（按需加载，可单独分发）────────────────┐
│  skills/ ×N  ≈461 行外移                              │
│  design-color · local-storage-safety · naming-system   │
│  visual-zoom-preview · single-source-arbitration       │
│  project-init · global-maintenance · code-traps         │
└───────────────────────────────────────────────────┘
```

### 为什么是这个形状（三条已验证的机制事实）

1. **plugin 不能注入常驻上下文**——包内放 `CLAUDE.md` 不会被当项目上下文加载，没有 `additionalDirectories` 类字段。→ 所以人格层**不能**靠 plugin 本身常驻。
2. **`SessionStart` hook 的 stdout 会作为上下文交给 Claude**（与 `UserPromptSubmit` 同类）。→ 所以可以用**指针**唤醒，而不是靠 skill 的 description 匹配。
3. **官方明说 Claude 倾向于 undertrigger skills**（skill-creator 原文：描述要写得"pushy"来对抗欠触发）。→ 这是把人格层交给 skill 的**决定性反对证据**，也是高危条目必须配哨兵行的理由。

> 层2 是 §八.3 **桥接指针制的第三次应用**（Memory 指针 → 高危哨兵行 → SessionStart 指针）。同一个解法在三个不同机制上复用成功 = 它已经是 HADE 体系里的一个**成熟模式**，不是临时补丁。

## §3 分层判定刀（可复用，不只用于这一轮）

每个条目过三问，答案唯一：

1. **缺了它，我还是 HADE 吗？** → 不是 → **常驻**，讨论结束
2. **它的触发场景能用一句话讲清楚吗？** → 能 → **候选 skill**
3. **触发失败的代价可逆吗？** → 不可逆（数据丢失 / 本体损伤） → **skill + Global 哨兵行**（双保险）

> 第 3 问是对机制事实 3 的直接防御：既然 Claude 会欠触发，那么"漏触发 = 数据没了"的条目就不允许只有一层保险。

## §6 SKILL.md 写法规格（这一轮的统一模板）

HADE 的 §七 四要素（触发/动作/原因/反例）**天然就是 skill 的结构**，一一对应：

```
触发  → YAML frontmatter 的 description（唯一的触发机制）
动作  → SKILL.md 正文
原因  → SKILL.md 正文
反例  → SKILL.md 正文（HADE 的反例是最强的唤醒锚，全部保留）
```

三条硬规格：

1. **description 必须"pushy"** —— 官方明确 Claude 倾向欠触发。写"设计色彩用这个"不够，要写"任何选色、做色板、定组件配色、甚至只是'挑个颜色'时都必须先读本 skill"。
2. **SKILL.md 正文 < 500 行**，超了就分 `references/` 子层（`visual-zoom-preview` 187 行、`single-source-arbitration` 129 行都在安全线内，直接平移）。
3. **中文照旧**（§七 读者模型：编码以 HADE 理解效率为准，中文无损且兼顾同步；换英文会切断与全部用户原话的连续性 —— 本轮不换）。

## §6.5 工具选型（浏览 skills 库后落定 · §八.12 调用规范）

已把可见的 skill 库全量过了一遍（本机 `/mnt/skills/**` 40 个 + 账号 marketplace）。结论按五步骨架：

### 用 —— 3 个

| 工具 | 用它的什么 | 用在哪一批 |
|------|-----------|-----------|
| **`skill-creator`**（已启用） | 写 skill 的规格 + **eval 机制** + **description 自动优化脚本** | 批1–批3 主力 |
| **`startup-hook-skill`**（本机已有） | SessionStart hook 的**机制知识**：stdin JSON、`$CLAUDE_PROJECT_DIR` / `$CLAUDE_ENV_FILE`、async 模式、注册写法、验证流程 | 批0 层2 |
| **`brand-guidelines` / `frontend-design`** | 只借**结构参照**：设计规范类 skill 怎么组织 | 批2 写 `design-color` 时 |

**`skill-creator` 里可直接用的现成脚本**（这是本次浏览最大的收获）：

- `scripts/run_eval.py` — 跑对照组，出触发率
- `scripts/run_loop.py` — **自动优化 description 的闭环**：60/40 训练/留出集拆分，每个 query 跑 3 次取可靠触发率，调 Claude 提改进版，最多迭代 5 轮，**按留出集分数选优**（防过拟合），出 HTML 报告
- `scripts/quick_validate.py` — SKILL.md 结构校验
- `scripts/package_skill.py` — 打包
- `agents/grader.md` · `comparator.md` — 评分与对照的现成 agent 定义

> `run_loop.py` 需要 `claude -p` CLI —— HADE 就跑在 Claude Code 里，**可用**。
> 这把 §7 的"触发率可测量"从设想变成了**现成仪器**：R1（触发欠敏）不再只有"description 写 pushy"这条原则，而是有了一个能给出数字、能自动迭代、能防过拟合的闭环。

### 不用 —— 3 个（这一半更重要）

| 工具 | 看着像 | 为什么不用 |
|------|--------|-----------|
| **`cowork-plugin-management`** | 名字就是"创建 plugin" | 它造的是 **Cowork 平台的 plugin**，HADE 跑在 **Claude Code** 里，目录结构与安装路径不是一回事。§八.12 第1步"防有锤子看啥都是钉子"的一次实际拦截 |
| **`engineering` plugin** | 含 architecture / documentation / tech-debt 等 skill | 与 §二 7步工作流**功能重叠但哲学冲突**。装它 = §九.18 经典陷阱：用业界标准替换你刻意设计的方案 |
| **`doc-coauthoring`** | 文档协作工作流 | 同上。§七 已经是一套更严的文档维护规则，引入第二套 = §七"不另开口子" |

### 空的一格

**没有任何现成 skill 覆盖"把一个大型规则文档拆成分层架构"这件事。** 批0 的分层判定、哨兵行设计、备份范围扩容——没有板，自己做。

### 沉淀什么（海，不是浪）

不记 `run_loop.py` 的参数（浪）。要沉淀的判断是：**「当一条规则的价值取决于它能否在对的时刻被唤起，就去找能给出触发率数字的工具，而不是靠自己判断'这条写得够不够醒目'」**——这是 §八.10 五问第1条"可触发性"第一次有了外部量具。此判断待批1 实测后，若成立再考虑进 Global（现在不进，§八.10 注：项目材料 ≠ Global 材料）。

## §6.6 第二层收益：把可判定的规则变成**可执行校验**（可选扩展 · 待确认）

> 来源：浏览 skills 库时发现 `dataviz` —— 它和 §十 色彩系统是**同一类物**（都在定"什么颜色能用、并置几种、什么场景收紧"），但它多带一个**可运行的配色校验器**。

### 发现

skill 的 `scripts/` 是**可执行层**——脚本能直接跑，**内容甚至不进上下文**。这意味着：

**凡是"可判定"的规则，都能从"要记住"变成"能跑"。**

HADE 体系里可判定的规则比想象中多：

| 规则 | 判定条件 | 校验脚本能做什么 |
|------|---------|-----------------|
| §十.1 禁区 | S 6–69% 严禁 | 扫颜色值，踩线直接报 |
| §十.6 密度 | 同屏色相 ≤ 6 | 数色相，超了报 |
| §十.7 并置 | 相邻色相间距 ≥ 30° | 算色相环距离 |
| §十.8 面积 | 大面积禁通道 A | 按元素尺寸判 |
| §九.24 | userData 路径必须 `setPath` 锁定 | 扫 `electron/main.js` |
| §九.25 | `deleteAppDataOnUninstall` 必须 `false` | 扫 `package.json` |
| §九.27 | 三件套齐备 | 三项逐个打勾 |

### 为什么这一步比 skill 化本身更重要（对高危条目）

**它把"概率触发"降级为"确定性检查"。**

R1（触发欠敏）对 §十 顶多是"这次配色平庸"；对 §九.I 是**数据不可逆丢失**。即使 skill 没被唤起，只要校验脚本被跑过一次，数据安全就有兜底。**哨兵行防的是"没想起来"，校验脚本防的是"想起来了但漏了一项"** —— 两种失败模式，两层保险。

**现成证据**：§十.9 的反例白纸黑字写着——OutingTool V2.0 选了 12 色全在 S≈54，"如果走过三问第 1 条就会被挡下"。**那正是一个校验脚本三秒钟能挡下的事**，却靠人工三问漏了，上线后"浑浊低级 / 太暗压抑 / 色相不协调"三症状齐发。

### 边界（这一条最容易越线，先钉住）

- ✅ **不违反 §1 非目标**：校验器只是把**已存在的数值约束**可执行化，一个字的规则内容都不改
- ⚠ **但它是新增能力，不是搬家**——超出"只动形式"的原始范围
- 所以列为**可选扩展**，不并入主路径，等你点头（见 §11 第 4 点）
- 若做，只做 §十 + §九.I 两个校验器（数值最硬、代价最不可逆），其余不碰

### 另一条随手落定的（无悬念，已直接采纳）

**机制事实必须核验，不靠训练记忆。** 本 Plan 整体架在几条机制断言上（hook stdout 会进上下文 / plugin 无法注入常驻上下文 / Claude 倾向欠触发）。平台在变，训练数据会过期。执行期每次涉及机制判断，走 `product-self-knowledge` skill 或官方文档核验 —— 这是 §三.10「禁止猜 → 要么提问要么验证」在平台机制维度的投影。

## §7 触发率验证 —— 这一轮真正的新能力

skill 机制自带 eval：同一个测试 prompt，同时跑**装了 skill** 和**没装 skill** 两组，对照结果。

**这是 HADE 体系里第一次，"可触发性"从自评变成实测数字。**

Global 里反复出现的自我诊断是同一句——**"规则写下 ≠ 被唤醒"**（05-31 日期翻车发生在刚写完 §八.10 的当口；06-09 发散期抢写文档，§六 的半条没在该触发时唤起）。这个病灶存在至今**没有任何测量手段**，只能靠用户事后抓到。

每个 skill 配 3 个真实场景 prompt 存 `evals/evals.json`，用 `skill-creator/scripts/run_eval.py` 跑对照组（见 §6.5）：

- 装了 skill 触发了 → description 合格
- 装了也没触发 → description 不够 pushy，改
- 没装也做对了 → 这条本来就是冗余（正好是 §八.10 五问第 3 条"不可推导"的**实测版**）

> 第三种结果尤其值钱：它能**证伪**条目，而不只是证实。现在的五问只能由 HADE 自己判"能不能从元规则推出来"——那是自我评估；eval 是外部证据。

## §8 分批节奏与验证门

| 批次 | 内容 | 门（过不了不进下一批） |
|------|------|----------------------|
| **批0 · 前置（安全，必须先做）** | ① Vault 备份范围扩到 `~/.claude/skills/**` 与 plugin 仓库 ② §七 破坏性预警**适用范围**同步扩容 ③ 建仓库骨架 + 全量备份当前状态 | 备份可还原验证通过 |
| **批1 · 零风险** | references ×3 → skill（本来就在 Global 外，且已经是按需读） | 3 个 skill 各跑 eval，触发率达标；真实 session 验证一次 |
