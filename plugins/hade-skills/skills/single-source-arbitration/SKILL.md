# 唯一仲裁源 — 多路径分配场景的数据流模式

> **何时读**：做"多个路径都可能改变某条数据归属（哪一类 / 哪一列 / 哪个分组 / 哪个状态）"的工具时。涉及拆分引擎、自动分类、规则匹配、跨行同步、批量传播。
>
> 从 2026-04-26 某文本转表格工具（文本转表格工具）的"名单表唯一源"重构提炼。多次 BUG 反复（拖拽分配后其他行不跟随、合并产物登记后散字段不匹配、传播路径绕过分类规则）的根因都是"没有唯一仲裁源"。

---

## 核心哲学

### 1. 一个事实，一个源头

任何"归属决策"（这条数据该分到哪）必须有**唯一一份权威数据**作为仲裁源。所有路径在做决策时都查询该源，不允许任何路径自行做"等价但旁路"的决策。

- **仲裁源** = 用户可见、可编辑的"分类规则表"（名单表 / 标签库 / 关键词词典 / 路由表）
- **非仲裁源** = 推断结果（cell.type='date'）、缓存（lastVerdict）、传播痕迹（mergePatterns）

仲裁源是**用户意图的固化**；其他都是从仲裁源派生的中间状态。

### 2. 任何"分配动作"都拆成两步

```
用户动作 → ① 写入仲裁源（addToSource）→ ② 触发全局重仲裁（rematchAll）
```

**禁止**：直接修改某条数据的归属（cell.assigned = X）而不写入仲裁源。这种旁路会让仲裁源和实际状态背离 — 下次重匹配时数据"忘了"自己被分过谁。

**典型反例**：propagateToAll 把同结构位置的格子强塞到目标列，但不写名单表 → 下次拆分相似文本时，相似格子又被识别为灰格（仲裁源根本不知道这条已被分类过）。

### 3. 传播职责必须拆分

多路径协同的工具里，至少有两类传播：

| 类型 | 例子 | 应该归谁 |
|------|------|---------|
| **结构传播** | 合并相邻 cell、批量打包、跨行同结构操作 | 独立机制（mergePatterns / groupRules） |
| **归属仲裁** | 这条数据该分到哪一列 / 哪个标签 | 唯一仲裁源（roster / labelMap） |

**关键**：结构传播 ≠ 归属传播。把它们混在一起 = 路径耦合 = 修一个 BUG 改三处。

某文本转表格工具 教训：原 `propagateToAll` 既做"跨行结构合并"又做"强塞归属"，重构后 → 结构合并归 mergePatterns，归属归名单表，propagateToAll 整个删除。

## 兑现规则（重仲裁函数的契约）

任何"全局重仲裁"函数（rematchAll / reclassifyAll）必须遵守：

### 铁律

**任何非手动数据**都要重走仲裁。**禁止按"原归属类型"或"数据 type"剪枝**。

### 唯一两个不动的例外

1. **用户手动锁定**（`auto === false && assigned !== null`）— 用户明确决策，仲裁源不可推翻
2. **类型推断专属路径**（`type === 'date' / 'time'` 之类的规则推断）— 不归仲裁源管，走另一套规则引擎（pattern matching / regex），与仲裁源解耦

### 动作矩阵

仲裁结果 = `auto` → 写入命中目标，标 auto，清歧义
仲裁结果 = `ambiguous` → 清归属，标歧义 + 候选列表，等用户裁决
仲裁结果 = `gray` 且非例外 type → 清归属（type 'classified' 降回 'unknown'）

### 反例（某文本转表格工具 修复前）

```js
// ❌ 按原归属类型剪枝 → 已分到非仲裁列的数据永远不被重查
if (col.type === 'roster') resolveAssign(text);

// ❌ 按数据 type 剪枝 → date/time 类型的数据无法被仲裁源覆盖（即使用户主动登记）
if (cell.type === 'unknown') resolveAssign(text);
```

修复后：所有非手动 cell 都走仲裁，date/time 在 gray 分支单独保留 — 是"动作矩阵中明确的例外"，不是"剪枝跳过"。

## 落地判断 — 哪些工具适用此模式

### 强适用

- **多类别归类工具**：邮件分类、文档分类、笔记打标签、CRM 联系人分组
- **拆分 + 分类**：文本转表格（某文本转表格工具）、日志解析、收据 OCR 字段归类
- **路由系统**：URL 路由、消息分发、任务派单
- **规则引擎**：折扣规则、风控规则、推荐规则

### 不适用

- **纯函数式数据流**：每次输入完全决定输出，无持久仲裁状态
- **单源工具**：只有一条路径会改归属（如纯手动表单）
- **概率型**：仲裁本身是概率分布而非二值（推荐系统排序）

### 适用度自检三问

动手前先答：
1. 我的工具有没有"用户可见的分类规则表"？（名单表 / 标签库 / 词典）
2. 是否有 ≥ 2 条路径会改某条数据的归属？（拖拽分配 / 合并产物 / 重匹配 / 批量操作）
3. 这些路径里有没有"不写规则表就改归属"的？

三问全是 → 强适用，立刻引入唯一仲裁源 + 登记重匹配链路。

## 某文本转表格工具 落地参考（具体实现）

详见 某文本转表格工具 SPEC §3.13。简要：

- **仲裁源** = 列名单表（roster），用户在名单表页可视化编辑
- **仲裁函数** = `resolveCellAssign(text)` → `{ kind: 'gray' | 'auto' | 'ambiguous', colIdx? }`
- **登记函数** = `addToRoster(colIdx, text)` — 把文本登记到对应列名单表
- **重仲裁函数** = `reMatchAllRows()` — 遍历所有 cell 走 resolveCellAssign，按动作矩阵更新
- **结构传播** = `mergePatterns`（每列独立的合并模式列表，与仲裁源解耦）
- **拖拽分配链路** = `executeBoxDrop` → `addToRoster + recordPattern + reMatchAllRows`

废弃：原 `propagateToAll` 函数已删除，"同结构位置强塞"逻辑彻底退役。

## 协作信号 — HADE 何时主动提议这套模式

用户描述的 BUG / 需求里出现以下信号 → HADE 主动提议引入唯一仲裁源：

- "改了 A 后 B 没跟上"（多路径不一致）
- "相同字段没匹配"（仲裁源未被全局应用）
- "拖到这边那边没反应"（路径间不通信）
- "传播太复杂"（结构 + 归属耦合）
- 用户连续修同一个"分配/分类"BUG ≥ 2 次

不要等用户提"要不要重构"，按文档体系主动判断 — 这条模式的引入成本（一个仲裁函数 + 一个重匹配函数 + 把所有路径改成"写源 + 重匹配"）通常远小于继续在多路径里打补丁的累积成本。
